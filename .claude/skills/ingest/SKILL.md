# ingest

人間が渡した資料(raw sources)を、素材 Markdown に分解して取り込みます。最後に Pull Request を作ります。

規則の詳細はリポジトリ直下の `CLAUDE.md` に従います。作業の前に必ず読んでください。

## 手順

1. **対象レイヤーを決める**
   - 指定がなければ `core` とします。
   - 非公開の資料(社内情報など)を `core` に入れようとしている場合は、作業を止めて人間に確認します。`core` は公開される前提です。

2. **資料を読む**
   - URL は取得して読みます。Obsidian のページなどローカルの資料はファイルを読みます。
   - 資料が取得できなかったら、推測で埋めずに人間に伝えます。

3. **分解案を作って人間に確認する**
   - 資料を「1 要素 = 1 素材」に分解し、次の内容を一覧にして提示します。
     - 論理 ID(パス)と一行要約
     - 新規か、既存素材の更新か
     - stance 案とその根拠
     - `depends_on` 案
     - 新しく必要なディレクトリやタグ
   - 既存の素材と重なるものがないか、対象レイヤーと上位レイヤーの README.md の索引で確かめます。重なる場合は、新規作成ではなく既存素材の更新として扱います。
   - 小さすぎる要素は親になる素材の節に吸収します。言語やツールに依存しない原則と、特定ツールの使い方は別の素材に分けます。
   - 資料だけでは中身が薄くなる要素は素材にせず、新規素材の候補として GitHub Issue に起票することを提案します。
   - **人間の承認を得てから次に進みます。**

4. **ブランチを作る**: `ingest/<要旨>`

5. **素材を書く**
   - `templates/material.md` をひな形にします。
   - frontmatter の `created` / `updated` は今日の日付、`models` は自分のモデル ID です。既存素材の更新では `updated` を今日にし、`models` に自分がいなければ追記します。
   - 方針節の冒頭に stance の理由を書きます。
   - 概要には、対象が何のためにあり、どんな課題をどう解決するのかを書きます。
   - ツールやライブラリは、公式のリポジトリやドキュメントを読み、解説に仕組みと使い方を書きます。資料の記事だけで済ませません。
   - `version` を持つ素材は、解説節の H3「メンテナンス状況」に、メンテナ、GitHub スター数、最新コミット日、最新リリース、確認日を書きます。GitHub のリポジトリなら `gh api repos/<owner>/<repo>` などで調べます。
   - 参考情報には公開ソースだけを書き、公式ドキュメントを先頭に置きます。取り込んだ資料が公開記事なら、それも書きます。
   - 履歴節には、新規なら `- YYYY-MM-DD: 新規作成。` を、更新で判断が変わったならその内容を追記します。
   - 素材どうしの方針に矛盾が出ないようにします。依存先の方針に合わせて書いた素材には `depends_on` を付けます。
   - 新しいタグは、そのレイヤーの `tags.yaml` に説明付きで登録します。

6. **推敲する**: 書いた素材を `yomiyasu` スキルで推敲します。意味や条件は変えません。

7. **検査する**

   ```sh
   uv run tools/hel.py index
   uv run tools/hel.py check
   ```

   エラーがなくなるまで直します。

8. **PR を作る**
   - タイトル例: `ingest: Go のテスト方針を追加`
   - 本文には次を書きます。
     - 取り込んだ資料(公開されている URL だけ)
     - 追加・更新した素材と、それぞれの stance
     - 判断に迷った点と、レビューで見てほしい点
     - 新しいディレクトリやタグを作った理由
   - Issue に起票した新規素材の候補があれば、そのリンクを書きます。
