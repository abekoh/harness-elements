# Go

## 概要

Go は Google で生まれたオープンソースのプログラミング言語です。静的型付けのコンパイル言語で、Web アプリケーションのバックエンド、CLI、インフラのツールなど、幅広い用途で使われます。

業務アプリケーションは長く運用され、そのあいだに担当者が入れ替わります。多機能なフレームワークや表現の選択肢が多い言語では、書き手ごとに書き方がばらつき、フレームワークが裏で何をしているかを知らないと読めないコードが増えます。破壊的変更のあるバージョンアップにも時間を取られます。Go は文法が小さく、書き方の選択肢が少ないため、誰が書いたコードでも読みやすくなります。アノテーションや独自の DSL のような隠れた仕組みも少なく、言語のバージョンを上げても既存のコードが動き続けることを公式に約束しています。

## 方針

文法が小さく「おまじない」が少ないため、担当者が入れ替わってもコードを読み続けられ、バージョンアップの負担も小さいため adopt とします。汎用の言語として、用途を問わず候補にします。

- バックエンド、CLI、ツールなど、汎用の用途で Go を使う。
- フレームワークは薄く使う。Web アプリケーションでは標準の `net/http` を基本にし、ルーティングやミドルウェアが厚くなるときだけ Echo などの軽いフレームワークを使う。アノテーションや独自の DSL に頼る仕組みは持ち込まない。
- アプリケーションの `go.mod` の `go` ディレクティブは最新の安定版に合わせ、新しいメジャーリリースが出たら早めに上げる。サポートされるのは最新の 2 つのメジャーリリースだけである。
- テスト・ダブルは [moq](../library/go/moq.md)、アサーションは [testify](../library/go/testify.md) を使う。

## 解説

### 言語の特徴

- **小さな文法**: キーワードは 25 個で、ループは `for` だけです。書き方の選択肢が少なく、書き手によるばらつきが出にくくなります。
- **`gofmt` による整形**: 標準の整形ツールでスタイルが 1 つに決まっていて、議論の余地がありません。import の整理もする `goimports`、`gofmt` より厳しい規則で整形する `gofumpt` などの選択肢もあります。
- **エラーは戻り値で返す**: 例外はなく、関数は `error` を戻り値で返します。エラー処理が明示的になる一方、`if err != nil` が続いて冗長になります。
- **ゴルーチンとチャネル**: 軽量なスレッド(ゴルーチン)と、その間でデータを受け渡すチャネルを言語が持っています。
- **単一のバイナリ**: 依存をまとめて 1 つの実行ファイルにでき、コンテナに載せやすくなります。
- **豊富な標準ライブラリ**: HTTP サーバ、JSON、テスト、暗号などが標準でそろいます。

ジェネリクスは 1.18 で、`slices` / `maps` パッケージは 1.21 で、イテレータ(`range` over func)は 1.23 で入りました。ただし、`filter` や `map` のような関数は標準にはなく、ループで書くか自分で定義します。

### 「おまじない」の少なさ

Spring Boot のアノテーションや Ruby on Rails の DSL は、覚えれば便利ですが、裏で多くのことをします。そのため、次の弱点があります。

- フレームワークの使い方だけで副読本が要るほど、学ぶことが多い。
- 中の動きを理解しないまま使えてしまい、技術を身につける機会が減る。
- 細かい挙動を変えたいときに変えにくい。
- バージョンごとに機能が増えたり挙動が変わったりして、覚え直しが要る。

Go の Web アプリケーションではアノテーションや DSL を使わず、素朴に書くのが一般的です。Echo のようなフレームワークを使っても、厚くなるのはルーティングとミドルウェアのあたりだけです。

### 互換性の約束

Go 1 の互換性の約束(Go 1 compatibility promise)により、Go 1 向けに書いたコードは、新しい Go 1.x でも変更なしにコンパイルして動くことが意図されています。約束の対象は言語仕様と標準ライブラリのコア API で、ソースの互換性です(バイナリの互換性ではありません)。セキュリティの修正、未規定の動作やバグへの依存、`unsafe` の使用などは例外です。

挙動を変える必要がある修正は、`GODEBUG` の設定で古い挙動に戻せるようになっています。`go.mod` の `go` ディレクティブで、どの挙動を使うかが決まります。1.21 からは `toolchain` ディレクティブで、使うツールチェーンのバージョンも指定できます。

メジャーリリースはおよそ半年に 1 回(2 月と 8 月)出ます。各メジャーリリースは、2 つ新しいメジャーリリースが出るまでサポートされます。

## トレードオフ

### 得られるもの

- 誰が書いても似たコードになり、担当者が入れ替わっても読み続けられる。
- 学ぶことが少なく、新しく入った人がすぐに書ける。
- 言語のバージョンアップの負担が小さい。
- 単一のバイナリで配布でき、起動が速い。

### 失われるもの

- `if err != nil` の繰り返しなどで、コードが冗長になる。
- `filter` / `map` のような高階関数や、例外、継承などの表現が標準にない。
- サードパーティのライブラリの成熟度にばらつきがあり、メンテナンスが止まることもある。

## 採用すべき？

### 採用すべきケース

- 長く運用し、担当者が入れ替わる業務アプリケーションのバックエンド。
- CLI、インフラのツール、コンテナで動かすサービス。
- 並行処理が多いサーバ。

### 採用すべきでないケース

- チームが別の言語とフレームワークに習熟していて、その生産性を手放すほどの理由がない。
- データ分析や機械学習など、ほかの言語のエコシステムが強い分野。
- ブラウザで動くフロントエンド。
