# Event Sourcing なしの CQRS

## 概要

読み込みと書き込みで実装を分けます(CQRS)。DB の分離や Event Sourcing は前提にせず、1 つの DB と 1 つの API のままで適用します。

## 方針

読み込みでドメインモデルを経由するコストを省けるため adopt とします。

- 読み込みは Query Service が SQL を直接発行し、レスポンス用の DTO を組み立てて返す。ドメインモデルは通さない。
- 書き込みはドメインモデルを通し、整合性はドメイン側で守る。
- DB は読み込み・書き込みで分けない。Event Sourcing も併用しない。
- 読み込み処理が冗長だと感じたら、読み込み専用のモデルを別に作ることを検討する。

## 解説

読み込みは状態を変えないため、整合性を守るための抽象化がいりません。ドメインモデルを組み立ててから DTO に変換すると、実装の手間がかかるうえ、必要のない列やテーブルまで読み込んでパフォーマンスも落ちます。SQL で必要なものだけを取るほうが効率的です。

CQRS は DB の分離や Event Sourcing と組み合わせて語られることが多いですが、どちらも必須ではありません。

## トレードオフ

### 得られるもの

- 一覧や集計など、複雑な読み込みを SQL で素直に書ける。
- 読み込みのパフォーマンスを個別に調整できる。

### 失われるもの

- 読み込みと書き込みで、同じテーブルを扱うコードが 2 系統になる。
- 読み込み側には、ドメインのルール(表示条件など)を SQL に重ねて書くことになる場合がある。

## 採用すべき？

### 採用すべきケース

- 画面や API ごとに、読み込む項目や結合が大きく異なる。
- ドメインモデルが複雑で、読み込みのたびに組み立てるコストが大きい。

### 採用すべきでないケース

- 単純な CRUD が中心で、読み込みと書き込みの形がほぼ同じ。
