# データとコードの分離

## 概要

エンティティはデータとして扱い、ドメインロジックはエンティティを引数で受け取るステートレスな関数に書きます。データ指向プログラミング(DOP)の原則の 1 つです。

## 方針

ロジックの置き場所に迷わず、純粋関数として単体テストしやすくなるため adopt とします。

- エンティティには状態を変えるメソッド(ミュータブル)も、新しい値を返すメソッド(イミュータブル)も持たせない。
- ただし、状態を表すだけのメソッド(文字列への変換、状態の判定など)は持たせてよい。
- ドメインロジックは必要なエンティティをすべて引数で受け取り、結果を返すステートレスな関数にする。
- DDD のドメインサービスは使わない。複数のエンティティにまたがる処理も、最初から関数として書く。
- 関数の入出力の型の付け方は [Input/Output の命名](input-output-naming.md) に従う。

## 解説

関連するエンティティが増えると、処理をどのエンティティのメソッドに置くか判断しにくくなり、ロジックが散らばります。ドメインサービスも置き場所の判断が難しく、同じ問題を起こします。

振る舞いを関数にまとめておけば、処理の置き場所で迷いません。DB の状態に依存する判定も、必要な値を引数で渡せば純粋関数になり、モックなしで単体テストできます([テストレベルの役割分担](../testing/test-level-roles.md))。

## トレードオフ

### 得られるもの

- ロジックの置き場所が一定になり、見通しがよくなる。
- 純粋関数になるため、単体テストを書きやすい。

### 失われるもの

- エンティティ自身が不変条件を守る、というオブジェクト指向の DDD の書き方から外れる。
- 関数の引数が増えやすい。

## 採用すべき？

### 採用すべきケース

- ドメインが複雑で、エンティティどうしの関連が多い。
- Go のように、クラスによるカプセル化を前提にしない言語を使う。

### 採用すべきでないケース

- エンティティのメソッドで不変条件を守る設計がチームで定着しており、うまく回っている。
