# 必要になるまで詳細を隠さない

## 概要

DB や外部コンポーネントをインタフェース(リポジトリなど)で抽象化するのは、必要になったときだけにします。必要かどうかは 3 つの条件で判断します。

## 方針

不要な抽象化は複雑さとコストを増やすだけなので adopt とします。

- 次のどれかに当てはまるときだけ、インタフェースで詳細を隠す。
  1. 同じインタフェースで、複数の DB や外部コンポーネントにつなぐ。
  2. 開発の途中で DB や外部コンポーネントが変わる可能性が高い。
  3. 統合テストで本物を再現するのが難しく、モックが必要になる。
- どれにも当てはまらなければ、DB や外部コンポーネントを直接呼ぶ。
- 条件 3 でモックを使う範囲は [モックは管理外の依存にだけ使う](../testing/mock-unmanaged-deps-only.md) に従う。

## 解説

「DB を差し替えられるように」と最初からリポジトリのインタフェースを用意しても、実際に差し替えることはまれです。インタフェースを挟むと、定義と実装の 2 か所を直すことになり、コードを読むときも実装へ飛びにくくなります。

テストのためにインタフェースを用意したくなる場面も多くありますが、DB は Testcontainers などで本物を使って統合テストできます。モックが本当に必要なのは、外部 API のように本物を再現しにくい依存です。

## トレードオフ

### 得られるもの

- 間接参照が減り、コードを追いやすい。
- インタフェースと実装を二重に直す手間がなくなる。

### 失われるもの

- 後から差し替えが必要になったときに、抽象化を入れる作業が発生する。

## 採用すべき？

### 採用すべきケース

- 使う DB や外部サービスがほぼ固定されている。
- 統合テストで本物の DB を使える。

### 採用すべきでないケース

- マルチテナントで DB の種類が違うなど、最初から条件 1 に当てはまる。
- プラグインのように、実装の差し替えそのものが要件になっている。
