# ホームリポパターン

## 概要

複数のリポジトリにまたがって AI エージェントを使うときの、ハーネスの置き場所の決め方です。エージェントを 1 つのリポジトリの中で起動すると、そのリポジトリしか見えません。スキルやエージェントの設定はリポジトリごとに複製され、リポジトリをまたぐ機能は全体を見ないまま設計することになります。

ホームリポパターンでは、共有するスキル、`AGENTS.md`、共有ドキュメントを 1 つの Git リポジトリ(ホームリポ)に集めます。エージェントはホームリポで起動し、ほかのリポジトリへは `AGENTS.md` に書いたポインタで辿ります。

## 方針

モノレポにできない複数リポジトリの環境で、ハーネスの重複をなくし、リポジトリをまたぐ作業を 1 つのセッションで進められるため adopt とします。モノレポにできるならモノレポのほうがよいので、recommended にはしません。

- 複数リポジトリにまたがる作業をするなら、ホームリポを 1 つ作り、エージェントはそこで起動する。
- ホームリポに置くもの: 複数リポジトリで共通のスキル、ポインタを書いた `AGENTS.md`、ステアリングファイル、共有ドキュメント(コーディング規約、用語集、システム全体の決定)、共有のツール。
- 各リポジトリに残すもの: コード、そのリポジトリ固有の `AGENTS.md`、ビルドとテストのコマンド、固有のドキュメント。履歴、リモート、Issue もリポジトリごとに持つ。
- ポインタは 1 リポジトリ 1 行で、名前、目的、ローカルのパスを書く。必要なら「変更前にそのリポジトリの `AGENTS.md` を読む」のような指示を添える。
- ポインタ先がローカルになければ、エージェントに clone させる。
- 同じリポジトリで複数のエージェントを並行して動かすときは、リポジトリの clone を 1 つにして、作業ごとに git worktree を切る。
- ハーネスが読むファイル(Claude Code なら `CLAUDE.md`)をホームリポに置き、本体の `AGENTS.md` を参照させる。
- `~/.claude/skills` のようなユーザーフォルダにスキルを置くのは、ホームリポを作るまでのつなぎとする。

## 解説

### 構成の例

```markdown
<!-- ホームリポの AGENTS.md -->
## リポジトリ

- Payments API: ~/repos/acme/payments-api。決済の API。変更前にそのリポジトリの AGENTS.md を読む。
- Web: ~/repos/acme/web。顧客向けのフロントエンド。
```

ホームリポは Git で版管理されるので、チームで共有でき、変更の履歴も残ります。ユーザーフォルダのスキルは個人の環境にしか残りません。

### 導入の手順

記事では、リポジトリを収めたフォルダでエージェントを起動し、専用のプロンプトを渡して次の 4 段階で移行します。計画を承認するまでエージェントは読むだけにし、`.env` のような秘密のファイルは読ませません。

1. リポジトリの棚卸し: 配下の Git リポジトリを探し、パス、リモート、公開範囲、最終コミット日を記録する。含めるリポジトリ、ホームリポの場所、個人用かチーム共有か、ハーネスが読むファイルを決める。
2. 共有素材の棚卸し: スキル、`AGENTS.md` や `CLAUDE.md`、エージェント向けのドキュメントを「共有」「重複」「リポジトリ固有」「インストール済み」に分ける。
3. 計画の合意: 項目と移動先の表、ホームリポの `AGENTS.md` 案を確認して承認する。
4. 適用: ホームリポを作り、共有素材をコピーし、子リポジトリ側の重複を新しいブランチで消してコミットする。push は人間が行う。

### 規模による変え方

- 20 程度のリポジトリなら、1 リポジトリ 1 行のポインタで足りる。
- 数百のリポジトリになると、ポインタが多すぎてエージェントが選べなくなる。事業領域ごとにポインタのファイルを分け、段階的に読ませる。
- 5〜10 程度のリポジトリなら submodule も使えるが、ポインタで同じことができる。
- 数千のリポジトリになるなら、スキルのマーケットプレイスで配るほうが向く。
- CI では、ホームリポをサンドボックスに置き、必要なリポジトリをエージェントに clone させる。

## トレードオフ

### 得られるもの

- スキルやエージェントの設定が 1 か所にまとまり、リポジトリごとの重複がなくなる。
- リポジトリをまたぐ機能を、全体を見ながら 1 つのセッションで計画できる。
- 共有のハーネスを Git で版管理し、チームで共有できる。
- 公開と非公開のリポジトリが混ざっていても、リポジトリを統合せずに済む。

### 失われるもの

- ポインタのパスや目的を、リポジトリの増減に合わせて保守する手間が増える。
- ホームリポと子リポジトリの両方に `AGENTS.md` があり、どちらに書くかの判断が要る。
- モノレポと違い、リポジトリをまたぐ変更を 1 つのコミットや PR にまとめられない。

## 採用すべき？

### 採用すべきケース

- 1 人またはチームで、複数のリポジトリを日常的に AI エージェントで扱う。
- 公開と非公開のリポジトリが混ざるなど、モノレポにできない事情がある。
- リポジトリごとに同じスキルや指示が複製されている。

### 採用すべきでないケース

- モノレポにできる。その場合はモノレポにする。
- 扱うリポジトリが 1 つだけ。
- 数千のリポジトリを扱う。スキルのマーケットプレイスで配るほうが向く。
