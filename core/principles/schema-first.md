# スキーマファースト

## 概要

API、DB、メッセージなど、システムの境界を流れるデータの形を、実装より先にスキーマとして定義します。型やクライアント、アクセス用のコードはスキーマから生成し、同じ知識を複数の場所で書きません。スキーマと実装、サーバとクライアントのずれによる修正漏れを防ぐための考え方です。

## 方針

スキーマの変更を 1 か所で済ませられ、修正漏れを防げるため adopt とします。生成の仕組みを整える手間や、生成ツールの制約とのトレードオフを考えたうえで採用します。

- 境界をまたぐデータの形は、言語に依存しないスキーマで先に定義し、それを正とする。
- 型、サーバのひな形、クライアント、データアクセスのコードはスキーマから生成する。
- 生成したコードは手で編集しない。
- フレームワークの仕組みでスキーマを一元管理できる場合は、コードを正にする書き方(Code First)でもよい。その場合もスキーマは 1 か所にする。
- 具体的な生成ツールは、言語ごとの素材で決める。

## 解説

スキーマの知識がコードとドキュメント、あるいはサーバとクライアントに分かれていると、片方だけを直す事故が起きます。DRY 原則を、コードだけでなくスキーマにも当てはめる考え方です。

スキーマを先に決めると、実装が終わる前でもサーバとクライアントの開発を並行して進められます。スキーマをレビューすれば、データの形の設計をコードより前に確かめられます。

### 適用する対象の例

| 対象 | スキーマの例 | 言語に依存しない生成ツールの例 |
| --- | --- | --- |
| REST API | OpenAPI | OpenAPI Generator |
| GraphQL API | GraphQL SDL | GraphQL Code Generator |
| メッセージ・RPC | Protocol Buffers、JSON Schema | buf |
| DB | マイグレーションの DDL、SQL | (言語ごとの素材で決める) |

DB では、マイグレーションや SQL を正とし、そこからアクセス用のコードを生成します。

## トレードオフ

### 得られるもの

- スキーマの変更が、型エラーとして利用箇所まで伝わる。
- 修正漏れによる不具合が減る。
- スキーマがそのまま仕様書になり、サーバとクライアントで並行して開発できる。

### 失われるもの

- 生成ツールの制約(対応していない構文、生成コードの形)に縛られる。
- ビルド手順に生成の工程が増える。
- スキーマ言語を書く手間と、それを学ぶコストがかかる。

## 採用すべき？

### 採用すべきケース

- API のサーバとクライアントを別々に実装している。
- 複数のサービスや言語が同じデータの形を扱う。
- DB のテーブルが多く、手書きのマッピングが負担になっている。

### 採用すべきでないケース

- 使い捨てのプロトタイプなど、スキーマがすぐに変わり、生成の仕組みを整えるほうが高くつく。
- 境界が 1 つの言語の中で閉じていて、型を共有すれば済む。
