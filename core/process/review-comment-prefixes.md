# レビューコメントのプレフィックス

## 概要

コードレビューのコメントの先頭に、`[MUST]` や `[IMO]` のような短いプレフィックスを付けて、コメントの種類を示す取り決めです。

プレフィックスのないコメントは、必ず直してほしい指摘なのか、個人の好みなのか、ただの質問なのかが文面からは分かりません。レビュイーはすべてを必須の指摘と受け取って対応に時間をかけたり、逆に重要な指摘を読み流したりします。レビュアーも強く言いすぎないよう言い回しに気を使います。プレフィックスで種類を先に示すと、レビュイーは対応の優先度を判断でき、レビュアーは意図をそのまま書けます。

## 方針

コメントの意図が一目で伝わり、やりとりの往復が減るため adopt とします。チームですでに別の取り決めがあるときは、そちらに従います。

- レビューコメントの先頭に、次の 4 つのプレフィックスのどれかを付ける。

  | プレフィックス | 意味 | レビュイーの対応 |
  | --- | --- | --- |
  | `[MUST]` | 必ず直してほしい指摘 | 直すまでマージしない |
  | `[IMO]` | In my opinion。レビュアー個人の意見や提案 | 採るかどうかはレビュイーが決める |
  | `[NITS]` | nitpick。細かい指摘や軽微な修正 | 直してもよいし、直さなくてもよい |
  | `[Q]` | Question。分からない点の質問 | 答える。答えに応じて直すこともある |

- `[MUST]` は強い指摘なので、理由を添え、言葉遣いに気をつける。
- AI エージェントがレビューするときも、同じプレフィックスを付けさせる。
- 初めて導入するチームではプレフィックスの意味を CONTRIBUTING.md や PR テンプレートに書いておく。

## 解説

### 似た取り決め

コメントの種類や重さを明示する取り決めは、ほかにもあります。

- **Google Engineering Practices**: `Nit:`(些細な指摘)、`Optional:` / `Consider:`(必須ではない提案)、`FYI:`(今回は対応不要な参考情報)の 3 つのラベルを勧めています。ラベルがないと、作成者はすべてのコメントを必須だと誤解しかねない、という理由です。
- **Conventional Comments**: `<label> [decorations]: <subject>` の形式を定めています。ラベルは `praise`、`nitpick`、`suggestion`、`issue`、`todo`、`question`、`thought`、`chore`、`note` などで、マージを止めるかどうかを `(blocking)` / `(non-blocking)` のデコレーションで別に示します。

本素材の 4 つのプレフィックスは、これらより種類が少なく、覚えることが少なくて済みます。種類と重さを分けて細かく示したいときは、Conventional Comments を使います。

### プレフィックスの対応関係

| 本素材 | Google | Conventional Comments |
| --- | --- | --- |
| `[MUST]` | (ラベルなし) | `issue (blocking)`、`todo` |
| `[IMO]` | `Optional:` / `Consider:` | `suggestion (non-blocking)`、`thought` |
| `[NITS]` | `Nit:` | `nitpick` |
| `[Q]` | (ラベルなし) | `question` |

### プレフィックスと組み合わせる習慣

取り込んだ note の記事では、プレフィックスとあわせて次の習慣も勧めています。

- レビュアーは PR の説明と関連 Issue を先に読んでから、コードを読む。
- 良いコードにもコメントする(Conventional Comments の `praise` にあたる)。
- 指摘したら、修正後に再レビューし、Approve まで見届ける。

## トレードオフ

### 得られるもの

- レビュイーがコメントごとの対応の優先度をすぐ判断できる。
- レビュアーが言い回しで強さを調整しなくても意図を伝えられる。
- `[MUST]` が残っているかどうかで、マージできるかを判断しやすい。

### 失われるもの

- 種類が 4 つしかないため、「良い点」や「参考情報」のようなコメントは書き分けられない。
- プレフィックスを知らない人には意味が伝わらず、最初に説明が要る。
- 機械で集計するには、Conventional Comments ほど形式が厳密ではない。

## 採用すべき？

### 採用すべきケース

- コードレビューをするチームで、コメントの強さの取り決めがまだない。
- 人と AI エージェントのレビューが混ざり、指摘の重さをそろえたい。

### 採用すべきでないケース

- チームですでに Conventional Comments などの取り決めを使っている。
- コメントの種類を機械で集計し、ツールで扱いたい(Conventional Comments のほうが向く)。
