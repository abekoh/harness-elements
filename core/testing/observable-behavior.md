# 観測可能な振る舞いを検証する

## 概要

テストでは、テスト対象が外から観測できる結果(戻り値、状態の変化、外部への出力)だけを検証します。内部でどう処理したかという実装の詳細は検証しません。

## 方針

リファクタリングでテストが壊れないようにするため adopt とします。

- 検証するのは、戻り値、永続化された状態、外部への出力(メール送信や外部 API へのリクエスト)だけにする。
- 内部で呼んだメソッドの順序や回数、依存に渡した引数は、外部への出力でない限り検証しない。
- 依存から値を受け取るだけのスタブについては、受け取った入力を検証しない([モックとスタブの使い分け](mock-vs-stub.md))。

## 解説

実装の詳細を検証するテストは、振る舞いが変わらないリファクタリングでも失敗します。これは偽陽性で、テストへの信頼を下げ、リファクタリングをためらわせます。

『単体テストの考え方/使い方』は、よいテストの性質として「リファクタリングへの耐性」を挙げ、観測可能な振る舞いだけを検証することでそれが得られるとしています。

## トレードオフ

### 得られるもの

- 振る舞いを変えないリファクタリングでテストが壊れない。
- テストが仕様の記述として読める。

### 失われるもの

- 内部の処理経路を細かく固定できないため、失敗したときの原因の切り分けに手間がかかる場合がある。

## 採用すべき？

### 採用すべきケース

- 常に採用する。

### 採用すべきでないケース

- なし
