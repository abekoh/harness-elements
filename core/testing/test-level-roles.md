# 単体テストと統合テストの役割分担

## 概要

単体テストと統合テストを定義で分け、それぞれが受け持つ範囲を決めます。ロジックの網羅は単体テストで行い、統合テストは全体がつながって動くことを確かめます。

## 方針

ロジックを速いテストで網羅しつつ、統合テストの数を抑えられるため adopt とします。

- 次の 3 条件をすべて満たすものを単体テストとし、満たさないものは統合テストとする。
  1. 1 単位の振る舞いを検証する。
  2. 実行時間が短い。
  3. ほかのテストから隔離されている。
- ドメインロジックは[データとコードの分離](../principles/data-code-separation.md) でステートレスな関数にし、正常系も異常系も単体テストで網羅する。
- 統合テストでは正常系の通しと、単体テストで拾えない箇所を確かめる。
- 単体テストで拾えない箇所には、次のものがある。
  - コントローラでのリクエストのバリデーション
  - DB の一意制約や外部キー制約
- これらはドメイン層に閉じ込められないため、ドメインの外に置いてよい。

## 解説

ドメインロジックを純粋関数にしておけば、DB や外部依存なしに単体テストで細かい分岐まで網羅できます。統合テストは遅く準備も重いため、すべての分岐を通そうとするとテストが増えすぎます。統合テストは「つながって動くこと」と「ドメインの外にしかないルール」に絞ります。

## トレードオフ

### 得られるもの

- テスト全体の実行時間が短くなる。
- 統合テストの数が抑えられ、保守しやすい。

### 失われるもの

- バリデーションや DB 制約のように、ルールの一部がドメインの外に残る。

## 採用すべき？

### 採用すべきケース

- ドメインロジックを純粋関数として切り出せる設計になっている。

### 採用すべきでないケース

- ロジックの大半が DB のクエリや外部サービスとのやりとりで、ドメインロジックがほとんどない。
